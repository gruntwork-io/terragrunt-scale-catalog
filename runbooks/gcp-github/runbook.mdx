# Bootstrap Gruntwork Pipelines — GCP + GitHub

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into a GitHub `infrastructure-live` repository and bootstraps it against one **GCP**
project. It handles both starting points:

- **A repository that is not yet set up for Terragrunt Scale.** The full repository layout is rendered
  into it — the root `root.hcl`, `.mise.toml`, `.gitignore`, `.gruntwork/`, the `.github/workflows`
  Pipelines workflows, and the first project's bootstrap stack.
- **A repository that already has a `root.hcl`.** Only the new project's directory and bootstrap stack
  are added; your existing configuration is left alone.

Which one applies is detected from the repository itself after it is cloned — you do not choose.

It then provisions, for that project, the Workload Identity Federation trust that lets your GitHub
Actions workflows authenticate to GCP with no long-lived credentials:

- a Workload Identity Pool and OIDC provider for GitHub Actions,
- a `plan` service account (read-only, used on pull requests), and
- an `apply` service account (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your GCP project
number comes from the project ID you provide, and the numeric GitHub org/repo IDs come from the clone
step. You only fill in what genuinely cannot be derived.

## 4. Select your infrastructure-live repository

Point this at the repository you want to manage with Pipelines. Everything generated below is written
into that clone.

## 5. Configure the bootstrap

Fill in the values that cannot be derived automatically. Everything else is supplied for you from the
steps above.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: ProjectName
    type: string
    description: A short human-readable name for this GCP project (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Project

  - name: GCPProjectID
    type: string
    description: The GCP project ID (e.g. "acme-dev-123456") you are bootstrapping. The numeric project number is derived automatically.
    validations:
      - required
    x-section: Project

  - name: GCPRegion
    type: string
    description: The GCP region used for the Google provider configuration and the GCS state bucket location.
    default: us-central1
    validations:
      - required
    x-section: Project

  - name: StateBucketName
    type: string
    description: Name of the GCS bucket for OpenTofu state. Must be globally unique and obey GCS bucket naming rules.
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC resources. Creates <prefix>-plan and <prefix>-apply service accounts and a <prefix>-pool Workload Identity Pool.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: IncludeDriftDetection
    type: bool
    description: Whether to render the scheduled drift-detection GitHub Actions workflow.
    default: true
    x-section: Advanced

  - name: OverwriteWorkflows
    type: bool
    description: When false (default), the CI workflow files are written only if they don't already exist, so bootstrapping an additional account into a repo that already has Pipelines won't overwrite (or revert customizations to) its workflows. Set true to force-refresh them.
    default: false
    x-section: Advanced

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1), or leave it as \"latest\" to use the newest release, resolved automatically before the generate step.'
    default: \"latest\"
    validations:
      - required
    x-section: Advanced

  - name: IaCTool
    type: enum
    description: 'The IaC binary Pipelines instructs Terragrunt to use. Gruntwork recommends OpenTofu; choose terraform only if your organisation requires it. A repository that already declares a tool keeps it — this choice applies to new configuration only.'
    options:
      - opentofu
      - terraform
    default: opentofu
    validations:
      - required
    x-section: Advanced

  - name: TerraformVersion
    type: string
    description: Terraform version to pin, used only when IaCTool is "terraform" and the repository has no mise config yet.
    default: "1.15.9"
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced
```
</Inputs>

## 9. Open a pull request

Commit the generated configuration and open a pull request against your repository. The commit is
tagged `[skip ci]`, so opening it does not start a Pipelines run — you have already applied the
bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.ProjectName }}/`. To add another project later, re-run this runbook
and choose a new `ProjectName`.
