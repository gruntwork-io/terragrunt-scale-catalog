# Bootstrap Gruntwork Pipelines — GCP + GitHub

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into a GitHub `infrastructure-live` repository and bootstraps it against one **GCP**
project. It handles both starting points:

- **A repository that is not yet set up for Terragrunt Scale.** The full repository layout is rendered
  into it — the root `root.hcl`, `.mise.toml`, `.gitignore`, `.gruntwork/`, the `.github/workflows`
  Pipelines workflows, and the first project's bootstrap stack.
- **A repository that already has a `root.hcl`.** Only the new project's directory and bootstrap stack
  are added; your existing configuration is left alone.

Which one applies is detected from the repository itself after it is cloned — you do not choose.

It then provisions, for that project, the Workload Identity Federation trust that lets your GitHub
Actions workflows authenticate to GCP with no long-lived credentials:

- a Workload Identity Pool and OIDC provider for GitHub Actions,
- a `plan` service account (read-only, used on pull requests), and
- an `apply` service account (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your GCP project
number comes from the project ID you provide, and the numeric GitHub org/repo IDs come from the clone
step. You only fill in what genuinely cannot be derived.

## 9. Open a pull request

Commit the generated configuration and open a pull request against your repository. The commit is
tagged `[skip ci]`, so opening it does not start a Pipelines run — you have already applied the
bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

If a branch of the same name is already on the remote from an earlier run, this fails and says so:
edit the branch name and run it again, or use the button it offers to delete the old branch first.

<GitHubPullRequest
  id="open-pr"
  title="Open the setup pull request"

/>

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .outputs.read_details.deploy_branch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .outputs.read_details.deploy_branch }}` for changes under `{{ .inputs.ProjectName }}/`. To add another project later, re-run this runbook
and choose a new `ProjectName`.
