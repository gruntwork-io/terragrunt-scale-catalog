# Bootstrap Gruntwork Pipelines — Azure + GitLab (existing repository)

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into an **existing** `infrastructure-live` repository hosted on **GitLab**, targeting
one **Azure** subscription.

It provisions, per subscription, the Entra ID (Azure AD) trust that lets your GitLab CI/CD pipelines
authenticate to Azure via OIDC federation with no long-lived secrets:

- an Entra ID application + service principal for `terragrunt plan` (read-only, used on merge requests),
- an Entra ID application + service principal for `terragrunt apply` (used on merges to your deploy branch),
- the federated identity credentials, custom roles, and role assignments that bind them to your
  GitLab group/project, and
- the Azure Blob Storage resource group, storage account, and container that hold OpenTofu state.

Wherever a value can be discovered automatically, this runbook does it for you — your Azure tenant ID
and subscription ID come from your authenticated `az` session, and the plan/apply application client IDs
are captured from the bootstrap output and written into your environment config. You only fill in what
genuinely cannot be derived.

<Admonition

  description="The bootstrap step creates Entra ID applications, service principals, federated credentials, custom roles, role assignments, and an Azure Blob Storage account in the subscription you authenticate to. Run this only against a subscription you own and intend to manage with Pipelines."

## 8. Ensure the Azure backend and providers in root.hcl

The bootstrap stack needs the repository `root.hcl` to declare the Azure `azurerm`/`azuread` providers and
an `azurerm` remote-state backend. In an existing Terragrunt Scale repo these are usually already present.
Below is the canonical configuration the runbook expects.

The remote-state backend is kept **commented out** while the state storage account is being created (the
first bootstrap runs against local state), and the runbook uncomments it automatically once the apply
succeeds.

<TemplateInline
  id="root-hcl-preview"
  inputsId={["deploy", "config"]}
  generateFile={false}
>
```hcl
// Reads the per-subscription state storage config from sub.hcl.
locals {
  _pipelines_sub_hcl = read_terragrunt_config(find_in_parent_folders("sub.hcl"))

  _pipelines_state_resource_group_name    = local._pipelines_sub_hcl.locals.state_resource_group_name
  _pipelines_state_storage_account_name   = local._pipelines_sub_hcl.locals.state_storage_account_name
  _pipelines_state_storage_container_name = local._pipelines_sub_hcl.locals.state_storage_container_name
}

# FIXME: Uncomment the code below when you've successfully bootstrapped Pipelines state.
# The runbook uncomments this automatically after the bootstrap apply succeeds.
# remote_state {
#   backend = "azurerm"
#   generate = {
#     path      = "backend.tf"
#     if_exists = "overwrite"
#   }
#   config = {
#     resource_group_name  = local._pipelines_state_resource_group_name
#     storage_account_name = local._pipelines_state_storage_account_name
#     container_name       = local._pipelines_state_storage_container_name
#     key                  = "${path_relative_to_include()}/tofu.tfstate"
#   }
# }

generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<EOF
provider "azurerm" {
  features {}

  resource_provider_registrations = "none"
}

provider "azuread" {}
EOF
}
```
</TemplateInline>

## 10. Provision the Azure resources

Plan first, review the output, then apply. Apply creates real resources (Entra ID applications, service
principals, federated credentials, custom roles, and the state storage account). The first apply runs
against **local** state; afterward the runbook captures the plan/apply client IDs, uncomments the remote
backend, and migrates state into the newly created storage account.

Commit the generated configuration and open a merge request against your repository. Opening the MR
does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup merge request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on merge requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.SubscriptionName }}/`. To add another subscription later, re-run
this runbook and choose a new `SubscriptionName`.
