# Bootstrap Gruntwork Pipelines — AWS + GitHub (new repository)

This runbook creates a **new** `infrastructure-live` repository on **GitHub**, scaffolds it as a full
[Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview) (Terragrunt Scale)
repository, and bootstraps Pipelines against one **AWS** account.

Because the repository starts empty, this runbook renders the entire repository layout for you — the root
`root.hcl`, `.mise.toml`, `.gitignore`, the `.github/workflows` Pipelines workflows (plan/apply, unlock,
and optionally drift detection), and the first account's bootstrap stack.

It then provisions, for that account, the OIDC trust that lets your GitHub Actions workflows authenticate
to AWS with no long-lived credentials:

- an IAM OpenID Connect provider for GitHub Actions,
- an IAM role for `terragrunt plan` (read-only, used on pull requests), and
- an IAM role for `terragrunt apply` (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your AWS account ID and
partition come from your authenticated identity, and the numeric GitHub org/repo IDs (used for GitHub's
immutable OIDC subject claims) are fetched with the `gh` CLI. You only fill in what genuinely cannot be
derived.

## 3. Create the repository

Choose where the new `infrastructure-live` repository should live and create it. The repository is created
empty; the following steps fill it with the Pipelines scaffold.

<Inputs id="repo" title="New repository">
```yaml
variables:
  - name: GitHubOrgName
    type: string
    description: The GitHub organization (or user) that will own the new repository.
    validations:
      - required
    x-section: Repository

  - name: GitHubRepoName
    type: string
    description: Name for the new infrastructure-live repository to create.
    default: infrastructure-live
    validations:
      - required
    x-section: Repository

  - name: Visibility
    type: enum
    description: Visibility of the new repository. "internal" requires a GitHub organization on a plan that supports internal repositories.
    options:
      - private
      - internal
    default: private
    validations:
      - required
    x-section: Repository
```
</Inputs>

## 6. Configure the bootstrap

Fill in the values that cannot be derived automatically. Everything else is supplied for you from the
steps above.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: AccountName
    type: string
    description: A short name for this AWS account (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Account

  - name: AWSRegion
    type: string
    description: The AWS region used for provider configuration and API calls when managing global resources.
    default: us-east-1
    validations:
      - required
    x-section: Account

  - name: StateBucketName
    type: string
    description: Name of the S3 bucket for OpenTofu state. Must be globally unique and obey S3 naming rules.
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC IAM resources. Creates <prefix>-plan and <prefix>-apply roles.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: DeployBranch
    type: string
    description: The branch Pipelines deploys from. Merges here trigger apply; this branch is granted the apply role.
    default: main
    validations:
      - required
    x-section: OIDC

  - name: IncludeDriftDetection
    type: bool
    description: Whether to generate the scheduled drift-detection workflow (.github/workflows/pipelines-drift-detection.yml).
    default: true
    x-section: Workflow

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced
```
</Inputs>

## 7. Generate the repository scaffold

Render the `aws/github/infrastructure-live` template into the empty repository. This writes the full
repository layout: `root.hcl`, `.mise.toml`, `.gitignore`, `.gruntwork/repository.hcl`, the
`.github/workflows/` Pipelines workflows (`pipelines.yml`, `pipelines-unlock.yml`, and — when drift
detection is enabled — `pipelines-drift-detection.yml`), `.gruntwork/environment-<AccountName>.hcl`,
`<AccountName>/account.hcl`, `<AccountName>/_global/region.hcl`, and the first account's bootstrap stack at
`<AccountName>/_global/bootstrap/terragrunt.stack.hcl`.

Before generating, resolve the latest catalog release so the bootstrap pins the newest version
automatically (unless you pinned a specific `TerragruntScaleCatalogRef` above).

<Command

## 9. Open a pull request

Commit the generated scaffold and open a PR against your new repository. Because the repository started
empty, this pull request seeds it with the Pipelines configuration; opening it does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.AccountName }}/`. To add another account later, use the
add-account runbook and choose a new `AccountName`.
