# Bootstrap Gruntwork Pipelines — GCP + GitLab (new repository)

This runbook creates a **new** `infrastructure-live` repository on **GitLab** and installs
[Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview) (Terragrunt Scale)
into it, targeting one **GCP** project.

It provisions, in that project, the Workload Identity Federation trust that lets your GitLab CI pipelines
authenticate to GCP with no long-lived service-account keys:

- a Workload Identity Pool and an OIDC provider for GitLab CI,
- a `plan` service account (read-only, used on merge requests), and
- an `apply` service account (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your GCP **project
number** is resolved from your project ID with `gcloud`, and the full repository scaffold (including the
`.gitlab-ci.yml` pipeline and the `.gruntwork/` environment config) is generated for you. You only fill
in what genuinely cannot be derived.

<Admonition
  type="warning"
  title="This provisions real cloud resources"
  description="The bootstrap step creates a Workload Identity Pool, an OIDC provider, plan/apply service accounts, and a GCS state bucket in the GCP project you authenticate to. Run this only against a project you own and intend to manage with Pipelines."
/>

<Admonition
  type="note"
  title="Prerequisite: configure SCM access for Pipelines"
  description="Gruntwork Pipelines needs access to your GitLab project to fetch your IaC code, reusable CI/CD code, and the Pipelines binary itself. Before you begin, set this up by configuring [machine users](https://docs.gruntwork.io/2.0/docs/pipelines/installation/viamachineusers) with Personal Access Tokens (PATs). This is separate from the GitLab sign-in this runbook uses to clone the project and open the merge request."

## 3. Configure the bootstrap

Fill in the values that cannot be derived automatically. Everything else — the GCP project number, the
repository scaffold, and the CI pipeline — is generated for you from the steps that follow.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: ProjectName
    type: string
    description: A short, human-readable name for this GCP project (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Project

  - name: GCPProjectID
    type: string
    description: The GCP project ID you are bootstrapping Pipelines in (the string identifier, e.g. "acme-prod-1a2b").
    validations:
      - required
    x-section: Project

  - name: GCPRegion
    type: string
    description: The GCP region used to configure the Google provider and the GCS state backend.
    default: us-central1
    validations:
      - required
    x-section: Project

  - name: StateBucketName
    type: string
    description: Name of the GCS bucket for OpenTofu state. Must be globally unique and obey GCS naming rules.
    validations:
      - required
    x-section: State

  - name: GitLabGroupName
    type: string
    description: The GitLab group (namespace) that will own the new repository, e.g. "acme". Cannot be derived — GitLab has no way to guess which group you mean.
    validations:
      - required
    x-section: GitLab

  - name: GitLabProjectName
    type: string
    description: The name of the new GitLab project (repository) to create, e.g. "infrastructure-live".
    default: infrastructure-live
    validations:
      - required
    x-section: GitLab

  - name: Visibility
    type: string
    description: 'Visibility of the new GitLab project: private, internal, or public.'
    default: private
    validations:
      - required
    x-section: GitLab

  - name: GitLabServerDomain
    type: string
    description: Domain of your GitLab server. Leave empty to use gitlab.com; set this for self-hosted GitLab instances (e.g. "gitlab.example.com").
    default: ""
    x-section: GitLab

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC resources. Creates <prefix>-pool, <prefix>-provider, and <prefix>-plan / <prefix>-apply service accounts.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: IncludeDriftDetection
    type: bool
    description: Whether to include the drift-detection workflow in the generated GitLab CI pipeline.
    default: true
    x-section: Advanced

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced
```
</Inputs>

## 5. Create the GitLab repository

Create the new, empty `infrastructure-live` repository in your GitLab group. It is initialized with a
README so the deploy branch exists and can be the target of the setup merge request.

Pipelines deploys from a single branch. Name it now — it becomes the new repository's initial branch, and
the setup merge request is opened against it.

<Inputs id="deploy" title="Deploy branch">
```yaml
variables:
  - name: DeployBranch
    type: string
    description: The branch Pipelines deploys from. Merges here trigger apply; this branch is granted the apply service account. Also becomes the new repository's default branch.
    default: main
    validations:
      - required
```
</Inputs>

## 10. Push and open a merge request

Commit the generated configuration on a feature branch, push it, and open a merge request against your
deploy branch. Opening the MR does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup merge request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on merge requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.ProjectName }}/`. To add another project later, re-run this runbook
against the same repository and choose a new `ProjectName`.
