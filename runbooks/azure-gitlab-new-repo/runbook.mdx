# Bootstrap Gruntwork Pipelines — Azure + GitLab (new repository)

This runbook creates a **new** `infrastructure-live` repository on **GitLab**, scaffolds it as a
[Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview) (Terragrunt Scale)
repo, and bootstraps it against one **Azure** subscription.

It provisions, per subscription, the OIDC (Azure Federated Identity) trust that lets your GitLab CI/CD
pipelines authenticate to Azure with no long-lived client secrets:

- an Entra ID application + service principal for `terragrunt plan` (read-only, used on merge requests),
- an Entra ID application + service principal for `terragrunt apply` (used on merges to your deploy branch),
- federated identity credentials scoped to your GitLab group/project, and
- the Azure Blob Storage account, container, and resource group that hold OpenTofu state.

Wherever a value can be discovered automatically, this runbook does it for you — your Azure tenant and
subscription IDs come from your authenticated identity, and the plan/apply client IDs are read back from
the bootstrap outputs and written into your Pipelines environment file. You only fill in what genuinely
cannot be derived.

<Admonition
  type="warning"
  title="This provisions real cloud resources"
  description="The bootstrap step creates Entra ID applications, service principals, custom role definitions and assignments, and an Azure Storage account for OpenTofu state in the subscription you authenticate to. Run this only against a subscription you own and intend to manage with Pipelines."
/>

<Admonition
  type="note"
  title="Prerequisite: configure SCM access for Pipelines"
  description="Gruntwork Pipelines needs access to your GitLab project to fetch your IaC code, reusable CI/CD code, and the Pipelines binary itself. This is separate from the GitLab sign-in this runbook uses to clone the project and open the merge request."

## 3. Configure the bootstrap

Fill in the values that cannot be derived automatically. The GitLab group/project and visibility drive the
next step (creating the repository); the rest are used later when scaffolding and provisioning.

<Admonition
  type="note"
  title="The GitLab group must already exist"
  description="This runbook creates a new project inside an existing group. Create the group in GitLab first (or use your personal namespace) and make sure your account can create projects in it."
/>

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: GitLabGroupName
    type: string
    description: The GitLab group (namespace) that will own the new project. The group must already exist and you must be able to create projects in it.
    validations:
      - required
    x-section: Repository

  - name: GitLabProjectName
    type: string
    description: The name of the new GitLab project to create (e.g. "infrastructure-live").
    default: infrastructure-live
    validations:
      - required
    x-section: Repository

  - name: Visibility
    type: string
    description: 'Visibility for the new GitLab project. One of: private, internal, public.'
    default: private
    validations:
      - required
    x-section: Repository

  - name: SubscriptionName
    type: string
    description: A short name for this Azure subscription (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Subscription

  - name: AzureLocation
    type: string
    description: The Azure region for the subscription's state-backend resources (e.g. "eastus").
    default: eastus
    validations:
      - required
    x-section: Subscription

  - name: StateResourceGroupName
    type: string
    description: Name of the Azure resource group that will hold the OpenTofu state storage account. Created by the bootstrap stack.
    validations:
      - required
    x-section: State

  - name: StateStorageAccountName
    type: string
    description: Name of the Azure storage account for OpenTofu state. Must be globally unique, 3-24 characters, lowercase letters and numbers only.
    validations:
      - required
    x-section: State

  - name: StateStorageContainerName
    type: string
    description: Name of the blob container for OpenTofu state within the storage account.
    default: tfstate
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC Entra ID resources. Creates <prefix>-plan and <prefix>-apply applications.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: Issuer
    type: string
    description: Override for the OIDC issuer URL. Leave blank for gitlab.com; set it only for self-hosted GitLab (e.g. https://gitlab.example.com).
    default: ""
    x-section: OIDC

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced

  - name: IncludeDriftDetection
    type: bool
    description: Whether to include the drift-detection workflow in the generated .gitlab-ci.yml.
    default: true
    x-section: Advanced
```
</Inputs>

## 4. Create the new GitLab repository

Create the empty project in your GitLab group. The next step clones it so the rest of the runbook can
write into the working copy.

Pipelines deploys from a single branch. Name it now — it becomes the new repository's initial branch, and
the setup merge request is opened against it.

<Inputs id="deploy" title="Deploy branch">
```yaml
variables:
  - name: DeployBranch
    type: string
    description: The branch Pipelines deploys from. Merges here trigger apply; this branch is granted the apply role.
    default: main
    validations:
      - required
```
</Inputs>

## 8. Generate the bootstrap configuration

Render the `azure/gitlab/infrastructure-live` template into the cloned repository. This writes `root.hcl`
(with the remote state backend commented out until after bootstrap), `.gitlab-ci.yml`, `.mise.toml`,

`{{ .inputs.SubscriptionName }}/sub.hcl`, and `{{ .inputs.SubscriptionName }}/bootstrap/terragrunt.stack.hcl`.

automatically (unless you pinned a specific `TerragruntScaleCatalogRef` above).

## 9. Provision the Azure resources

Plan first, review the output, then apply. Apply creates real resources (Entra ID applications, service
principals, custom roles, federated credentials, and the Azure Blob state storage). The bootstrap runs with
**local** state because the state storage account does not exist yet — you migrate to remote state in a
later step.

## 12. Open a merge request

Push the scaffold to the deploy branch, put the generated configuration on a feature branch, and open a
merge request. Opening the MR does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup merge request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on merge requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.SubscriptionName }}/`. To add another subscription later, render the
`azure/gitlab/subscription` template with a new `SubscriptionName` and bootstrap it the same way.
