# Bootstrap Gruntwork Pipelines — AWS + GitLab (new repository)

This runbook creates a **new** `infrastructure-live` repository on **GitLab**, scaffolds it as a full
[Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview) (Terragrunt Scale)
repository, and bootstraps Pipelines against one **AWS** account.

Because the repository starts empty, this runbook renders the entire repository layout for you — the root
`root.hcl`, `.mise.toml`, `.gitignore`, `.gruntwork/repository.hcl`, the `.gitlab-ci.yml` Pipelines CI
pipeline, and the first account's bootstrap stack.

It then provisions, for that account, the OIDC trust that lets your GitLab CI/CD jobs authenticate to AWS
with no long-lived credentials:

- an IAM OpenID Connect provider for GitLab CI,
- an IAM role for `terragrunt plan` (read-only, used on merge requests), and
- an IAM role for `terragrunt apply` (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your AWS account ID and
partition come from your authenticated identity. GitLab has no numeric immutable-claim mechanism, so the
OIDC trust is scoped by **group** and **project** name; you supply those (and the other non-derivable
settings) in the form.

## 4. Configure the bootstrap

Fill in the values that cannot be derived automatically. Your GitLab group and project names cannot be
reliably derived, so you provide those here; everything else that can be discovered is supplied for you
from the steps above and below.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: AccountName
    type: string
    description: A short name for this AWS account (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Account

  - name: AWSRegion
    type: string
    description: The AWS region used for provider configuration and API calls when managing global resources.
    default: us-east-1
    validations:
      - required
    x-section: Account

  - name: GitLabGroupName
    type: string
    description: The GitLab group (or top-level namespace) that will own the new project. Only CI jobs in this group/project may assume the IAM roles.
    validations:
      - required
    x-section: GitLab

  - name: GitLabProjectName
    type: string
    description: Name for the new infrastructure-live project to create (the repository's path within the group).
    default: infrastructure-live
    validations:
      - required
    x-section: GitLab

  - name: Visibility
    type: enum
    description: Visibility of the new GitLab project. "internal" is visible to any authenticated user on the instance; "private" is restricted to members.
    options:
      - private
      - internal
    default: private
    validations:
      - required
    x-section: GitLab

  - name: StateBucketName
    type: string
    description: Name of the S3 bucket for OpenTofu state. Must be globally unique and obey S3 naming rules.
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC IAM resources. Creates <prefix>-plan and <prefix>-apply roles.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: Issuer
    type: string
    description: OIDC issuer URL override. Leave as "default" for gitlab.com; set this to your instance URL only for self-hosted GitLab (e.g. https://gitlab.example.com).
    default: "default"
    validations:
      - required
    x-section: Advanced

  - name: TerragruntScaleCatalogRef
    type: enum
    description: Which terragrunt-scale-catalog version this bootstrap pins. Leave it on latest to use the newest release, resolved when the generate step runs. Pick a tag instead to pin one explicitly.
    # Regenerated by scripts/update-catalog-refs.sh -- do not hand-edit.
    options:
      - latest
      - v1.13.2
      - v1.13.1
      - v1.13.0
      - v1.12.2
      - v1.12.1
      - v1.12.0
      - v1.11.3
      - v1.11.2
      - v1.11.1
      - v1.11.0
    default: latest
    validations:
      - required
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.

    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced

## 5. Create the GitLab project

Create the new, empty `infrastructure-live` project in your group. The following steps fill it with the
Pipelines scaffold.

Pipelines deploys from a single branch. Name it now — it becomes the new repository's initial branch, and
the setup merge request is opened against it.

<Inputs id="deploy" title="Deploy branch">

variables:
  - name: DeployBranch
    type: string
    description: The branch Pipelines deploys from. Merges here trigger apply; this branch is granted the apply role.
    default: main
    validations:
      - required
```
</Inputs>

## 7. Generate the repository scaffold

Render the `aws/gitlab/infrastructure-live` template into the empty repository. This writes the full
repository layout: `root.hcl`, `.mise.toml`, `.gitignore`, `.gruntwork/repository.hcl`, the

## 9. Open a merge request

Commit the generated scaffold, push a setup branch, and open a merge request against your new repository.
Because the repository started empty, this seeds it with the Pipelines configuration; opening the merge
request does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

Once it merges, Pipelines runs apply for changes under your account directory."

**You're done.** The setup merge request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on merge requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.AccountName }}/`. To add another account later, use the
add-account runbook and choose a new `AccountName`.
