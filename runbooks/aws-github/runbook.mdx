# Bootstrap Gruntwork Pipelines — AWS + GitHub

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into a GitHub `infrastructure-live` repository and bootstraps it against one **AWS**
account. It handles both starting points:

- **A repository that is not yet set up for Terragrunt Scale.** The full repository layout is rendered
  into it — the root `root.hcl`, `.mise.toml`, `.gitignore`, `.gruntwork/`, the `.github/workflows`
  Pipelines workflows, and the first account's bootstrap stack.
- **A repository that already has a `root.hcl`.** Only the new account's directory and bootstrap stack
  are added; your existing configuration is left alone.

Which one applies is detected from the repository itself after it is cloned — you do not choose.

It then provisions, for that account, the OIDC trust that lets your GitHub Actions workflows authenticate
to AWS with no long-lived credentials:

- an IAM OpenID Connect provider for GitHub Actions,
- an IAM role for `terragrunt plan` (read-only, used on pull requests), and
- an IAM role for `terragrunt apply` (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your AWS account ID and
partition come from your authenticated identity, and the numeric GitHub org/repo IDs (used for GitHub's
immutable OIDC subject claims) come from the clone step. You only fill in what genuinely cannot be
derived.

## 7. Set up the repository

Existing OIDC providers and IAM roles are reconciled before anything is generated, using the prefix
you chose above. What it finds is matched against the answers in the **Existing resources** section.

<Command
  id="plan-imports"
  title="Reconcile existing AWS resources"
  description="Looks for a GitHub OIDC provider and for `<prefix>-plan` / `<prefix>-apply` roles, their policies and attachments, and decides which of them the bootstrap should import rather than create. Stops with an explanation if something exists that you asked not to import."
  inputsId="config"
  awsAuthId="aws-auth"
  path="scripts/plan-imports.sh"
/>

Everything the repository needs is written in one pass: the Terragrunt Scale configuration, the tool
versions it pins, the Pipelines CI workflows, and a README. Each phase is logged separately, and if one
fails the run stops there and names it.

<Command
  id="setup-repository"
  title="Set up the repository"
  description="Runs four phases in order: renders the Terragrunt Scale configuration with `boilerplate`, runs `mise install` for the Terragrunt and OpenTofu versions it pins, adds the Pipelines CI workflows (existing ones are left alone unless `OverwriteWorkflows` is set), and writes the README — as `README.md` when the repository has none or only a stub, otherwise as `README.template.md` alongside the existing one."
  inputsId="config"
  path="scripts/setup-repository.sh"

## 8. Provision the AWS resources

Plan first, review the output, then apply. Apply creates real resources (OIDC provider, IAM roles, and
the S3 state bucket via `--backend-bootstrap`). The last step reads them back out of AWS so you can see
exactly what now exists in the account, and documents it inside that account's own folder: a diagram
the **Changed files** panel on the right renders as an image, plus a README of its identifiers. Each
account bootstrapped into this repository gets its own pair, and both are committed with the rest of
the configuration.

<Command
  id="bootstrap-plan"

## 9. Open a pull request

Commit the generated configuration and open a pull request against your repository. The commit is tagged
`[skip ci]`, so opening it does not start a Pipelines run — you have already applied the bootstrap
locally. After it merges to your deploy branch, Pipelines takes over.

If a branch of the same name is already on the remote from an earlier run, this fails and says so:
edit the branch name and run it again, or use the button it offers to delete the old branch first.

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .outputs.read_details.deploy_branch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .outputs.read_details.deploy_branch }}` for changes under `{{ .inputs.AccountName }}/`. To add another account later, re-run this runbook against the same repository and choose a new `AccountName`.
