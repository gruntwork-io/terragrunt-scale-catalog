# Bootstrap Gruntwork Pipelines — Azure + GitHub (existing repository)

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into an **existing** `infrastructure-live` repository hosted on **GitHub**, targeting
one **Azure** subscription.

It provisions, per subscription, the OIDC (Federated Identity) trust that lets your GitHub Actions
workflows authenticate to Azure with no long-lived secrets:

- an Entra ID application + service principal for `terragrunt plan` (read-only, used on pull requests),
- an Entra ID application + service principal for `terragrunt apply` (used on merges to your deploy branch),
- the flexible/static federated identity credentials and least-privilege custom roles that back them, and
- the Azure Blob Storage backend (Resource Group, Storage Account, Container) for OpenTofu state.

Wherever a value can be discovered automatically, this runbook does it for you — your Azure tenant and
subscription IDs come from your `az` session, and the numeric GitHub org/repo IDs (used for GitHub's
immutable OIDC subject claims) come from the clone step. It even reads the App Registration client
IDs back out of the bootstrap outputs and writes them into your environment config, so there are no
manual FIXME edits left behind. You only fill in what genuinely cannot be derived.

<Admonition

## 8. Ensure the repository root configuration

The subscription template does **not** create `root.hcl` (it lives in the `azure/base` layer that only
brand-new repos pull in). For an existing repo we add the same content: the `azurerm`/`azuread` provider
generation plus a `remote_state` block, left commented out until state is bootstrapped and migrated.

Here's the exact block that will be added if your `root.hcl` doesn't already configure `remote_state`:

<TemplateInline
  id="root-hcl-preview"
  generateFile={false}
>
```hcl
// Root Terragrunt config included by every unit via `find_in_parent_folders("root.hcl")`.
// Generates the Azure provider for all units. Remote state is commented out until after bootstrap.
// Docs: https://docs.terragrunt.com/reference/config-blocks-and-attributes/#remote_state

// Read environment-level config from the nearest parent files.
locals {
  sub_hcl = read_terragrunt_config(find_in_parent_folders("sub.hcl"))

  state_resource_group_name    = local.sub_hcl.locals.state_resource_group_name
  state_storage_account_name   = local.sub_hcl.locals.state_storage_account_name
  state_storage_container_name = local.sub_hcl.locals.state_storage_container_name
}

# FIXME: Uncomment the code below when you've successfully bootstrapped Pipelines state.
#
# remote_state {
#   backend = "azurerm"
#   generate = {
#     path      = "backend.tf"
#     if_exists = "overwrite"
#   }
#   config = {
#     resource_group_name  = local.state_resource_group_name
#     storage_account_name = local.state_storage_account_name
#     container_name       = local.state_storage_container_name
#     key                  = "${path_relative_to_include()}/tofu.tfstate"
#   }
# }

// Generates provider.tf in each unit at plan/apply time.
// `resource_provider_registrations = "none"` prevents the provider from auto-registering resource providers, which needs elevated permissions.
// Docs: https://search.opentofu.org/provider/terraform-providers/azurerm/latest
generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<EOF
provider "azurerm" {
  features {}

  resource_provider_registrations = "none"
}

provider "azuread" {}
EOF
}
```
</TemplateInline>

## 10. Provision the Azure resources

Plan first, review the output, then apply. Apply creates real resources: the state Resource Group,
Storage Account, and Container, plus the plan/apply Entra ID applications, service principals, federated
credentials, custom roles, and role assignments.

Note there is no `--backend-bootstrap` on Azure — the first apply runs against **local** state and creates
the Storage Account as a resource. We migrate the state into it in the next section.

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.SubscriptionName }}/`. To add another subscription later, re-run
this runbook and choose a new `SubscriptionName`.
