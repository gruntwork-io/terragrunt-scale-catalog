# Bootstrap Gruntwork Pipelines — GCP + GitHub (existing repository)

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into an **existing** `infrastructure-live` repository hosted on **GitHub**, targeting
one **GCP** project.

It provisions, per project, the Workload Identity Federation trust that lets your GitHub Actions
workflows authenticate to GCP with no long-lived credentials:

- a Workload Identity Pool and Provider for GitHub Actions,
- a service account for `terragrunt plan` (read-only, used on pull requests), and
- a service account for `terragrunt apply` (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your GCP project number
comes from `gcloud projects describe`, and the numeric GitHub org/repo IDs (used for GitHub's immutable
OIDC subject claims) come from the clone step. You only fill in what genuinely cannot be derived.

<Admonition
  type="warning"
  title="This provisions real cloud resources"
  description="The bootstrap step creates a Workload Identity Pool, plan/apply service accounts with IAM bindings, and a GCS state bucket in the GCP project you authenticate to. Run this only against a project you own and intend to manage with Pipelines."
/>

<Admonition
  type="note"

## 5. Configure the bootstrap

Fill in the values that cannot be derived automatically. Everything else is supplied for you from the
steps above.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: ProjectName
    type: string
    description: A short human-readable name for this GCP project (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Project

  - name: GCPProjectID
    type: string
    description: The GCP project ID (e.g. "acme-dev-123456") you are bootstrapping. The numeric project number is derived automatically.
    validations:
      - required
    x-section: Project

  - name: GCPRegion
    type: string
    description: The GCP region used for the Google provider configuration and the GCS state bucket location.
    default: us-central1
    validations:
      - required
    x-section: Project

  - name: StateBucketName
    type: string
    description: Name of the GCS bucket for OpenTofu state. Must be globally unique and obey GCS bucket naming rules.
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC resources. Creates <prefix>-plan and <prefix>-apply service accounts and a <prefix>-pool Workload Identity Pool.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: OverwriteWorkflows
    type: bool
    description: When false (default), the CI workflow files are written only if they don't already exist, so bootstrapping an additional account into a repo that already has Pipelines won't overwrite (or revert customizations to) its workflows. Set true to force-refresh them.
    default: false
    x-section: Advanced

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced
```
</Inputs>

## 6. Generate the bootstrap configuration

First derive the numeric GCP project number from the project ID you entered above.

<Command
  id="derive-gcp"
  title="Resolve the GCP project number"
  description="Runs `gcloud projects describe` to derive the numeric project number from your project ID."
  inputsId={["deploy", "config"]}
  path="scripts/derive-gcp.sh"
/>

Then render the `gcp/github/project` template into your repository. This writes
`<ProjectName>/bootstrap/terragrunt.stack.hcl`, `<ProjectName>/project.hcl`, and
`.gruntwork/environment-<ProjectName>.hcl` (fully populated — no manual client-id step is needed).

Before generating, resolve the latest catalog release so the bootstrap pins the newest version
automatically (unless you pinned a specific `TerragruntScaleCatalogRef` above).

<Command
  id="resolve-catalog-ref"
  title="Resolve the latest catalog release"
  description="Runs `git ls-remote` to find the newest terragrunt-scale-catalog release tag, used as the catalog ref for the generate step unless you pinned one."
  path="scripts/resolve-catalog-ref.sh"
/>

<Command
  id="generate-bootstrap"
  title="Render the project template"
  description="Runs `boilerplate` non-interactively with your form values and the auto-derived IDs."
  inputsId={["deploy", "config"]}
  path="scripts/generate-bootstrap.sh"
/>

Now install the Terragrunt and OpenTofu versions pinned for the repository:

<Command

## 7. Add the GitHub Actions workflow

Add the Pipelines GitHub Actions workflows — the plan/apply workflow plus the unlock and
drift-detection workflows. Each file is written only if it is missing, so re-running this against a
repo that already has Pipelines (for example when adding another account) won't clobber your
workflows; set `OverwriteWorkflows` in the form above to force-refresh them.

<Command
  id="add-ci-workflows"

  description="Writes the plan/apply, unlock, and drift-detection GitHub Actions workflows into the repo. Each file is written only if it does not already exist, so bootstrapping an additional account into a repo that already has Pipelines will not overwrite its workflows — set \`OverwriteWorkflows\` above to force-refresh them."

## 8. Provision the GCP resources

Plan first, review the output, then apply. Apply creates real resources (Workload Identity Pool and
Provider, plan/apply service accounts and IAM bindings, and the GCS state bucket via
`--backend-bootstrap`).

## 9. Open a pull request

Commit the generated configuration and open a PR against your repository. Opening the PR does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.ProjectName }}/`. To add another project later, re-run this runbook
and choose a new `ProjectName`.
