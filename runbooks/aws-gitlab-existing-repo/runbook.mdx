# Bootstrap Gruntwork Pipelines — AWS + GitLab (existing repository)

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into an **existing** `infrastructure-live` repository hosted on **GitLab**, targeting
one **AWS** account.

It provisions, per account, the OIDC trust that lets your GitLab CI/CD jobs authenticate to AWS with no
long-lived credentials:

- an IAM OpenID Connect provider for GitLab CI,
- an IAM role for `terragrunt plan` (read-only, used on merge requests), and
- an IAM role for `terragrunt apply` (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your AWS account ID and
partition come from your authenticated identity. GitLab has no numeric immutable-claim mechanism, so the
OIDC trust is scoped by **group** and **project** name; you supply those (and the other non-derivable
settings) in the form.

<Admonition
  type="warning"
  title="This provisions real cloud resources"
  description="The bootstrap step creates IAM roles, an OIDC provider, and an S3 state bucket in the AWS account you authenticate to. Run this only against an account you own and intend to manage with Pipelines."
/>

<Admonition
  type="note"
  title="Prerequisite: configure SCM access for Pipelines"
  description="Gruntwork Pipelines needs access to your GitLab project to fetch your IaC code, reusable CI/CD code, and the Pipelines binary itself. Before you begin, set this up by configuring [machine users](https://docs.gruntwork.io/2.0/docs/pipelines/installation/viamachineusers) with Personal Access Tokens (PATs). This is separate from the GitLab sign-in this runbook uses to clone the project and open the merge request."
/>

## 6. Configure the bootstrap

Fill in the values that cannot be derived automatically. Everything else is supplied for you from the
steps above.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: AccountName
    type: string
    description: A short name for this AWS account (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Account

  - name: AWSRegion
    type: string
    description: The AWS region used for provider configuration and API calls when managing global resources.
    default: us-east-1
    validations:
      - required
    x-section: Account

  - name: GitLabGroupName
    type: string
    description: The GitLab group (or top-level namespace) that owns the project. Only CI jobs in this group/project may assume the IAM roles.
    validations:
      - required
    x-section: GitLab

  - name: GitLabProjectName
    type: string
    description: The GitLab project name (the repository's path within the group).
    validations:
      - required
    x-section: GitLab

  - name: StateBucketName
    type: string
    description: Name of the S3 bucket for OpenTofu state. Must be globally unique and obey S3 naming rules.
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC IAM resources. Creates <prefix>-plan and <prefix>-apply roles.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: DeployBranch
    type: string
    description: The branch Pipelines deploys from. Merges here trigger apply; this branch is granted the apply role.
    default: main
    validations:
      - required
    x-section: OIDC

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced

  - name: Issuer
    type: string
    description: OIDC issuer URL override. Leave blank for gitlab.com; set this to your instance URL only for self-hosted GitLab (e.g. https://gitlab.example.com).
    default: ""
    x-section: Advanced
```
</Inputs>

## 7. Generate the bootstrap configuration

Render the `aws/gitlab/account` template into your repository. This writes
`<AccountName>/_global/bootstrap/terragrunt.stack.hcl`, `<AccountName>/account.hcl`,
`<AccountName>/_global/region.hcl`, and `.gruntwork/environment-<AccountName>.hcl`.

Before generating, resolve the latest catalog release so the bootstrap pins the newest version
automatically (unless you pinned a specific `TerragruntScaleCatalogRef` above).

## 8. Add the GitLab CI workflow

An existing repository needs the Pipelines CI workflow added explicitly (the account template does not
include it). This writes `.gitlab-ci.yml` at the repo root, including the Pipelines CI component from
your GitLab instance.

<TemplateInline
  id="workflow-file"

## 10. Open a merge request

Commit the generated configuration, push a setup branch, and open a merge request against your
repository. Opening the MR does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

<Command
  id="merge-request"
  title="Open the setup merge request"
  description="Creates a branch, commits the generated files, pushes, and opens a merge request via `glab`."
  inputsId="config"
  gitlabAuthId="gitlab-auth"
  path="scripts/open-merge-request.sh"
/>

<Admonition
  type="note"
  title="If glab isn't available"
  description="The script pushes the setup branch either way. If `glab` cannot open the merge request automatically, just open one in the GitLab UI from the pushed branch — pushing the branch is all that's required to trigger the Pipelines plan."
/>

**You're done.** The setup merge request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on merge requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.AccountName }}/`. To add another account later, re-run this runbook
and choose a new `AccountName`.
