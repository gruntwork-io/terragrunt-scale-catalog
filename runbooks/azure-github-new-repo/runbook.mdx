# Bootstrap Gruntwork Pipelines — Azure + GitHub (new repository)

This runbook creates a **new** `infrastructure-live` repository on **GitHub**, scaffolds it as a full
[Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview) (Terragrunt Scale)
repository, and bootstraps Pipelines against one **Azure** subscription.

Because the repository starts empty, this runbook renders the entire repository layout for you — the root
`root.hcl`, `.mise.toml` (pinning Terragrunt, OpenTofu, the Azure CLI, and Python), `.gitignore`, the
`.github/workflows` Pipelines workflows (plan/apply, unlock, and optionally drift detection), and the
first subscription's bootstrap stack.

It then provisions, for that subscription, the Entra ID (Azure AD) trust that lets your GitHub Actions
workflows authenticate to Azure with no long-lived secrets:

- an Entra ID application + service principal for `terragrunt plan` (read-only, used on pull requests),
- an Entra ID application + service principal for `terragrunt apply` (used on merges to your deploy branch),
- federated identity credentials binding each application to your repository's OIDC tokens, and
- the Azure Blob Storage resources (resource group, storage account, and container) that hold OpenTofu state.

Wherever a value can be discovered automatically, this runbook does it for you — your Azure tenant and
subscription IDs come from your authenticated `az` session, and the numeric GitHub org/repo IDs (used for
GitHub's immutable OIDC subject claims) come from the clone step. You only fill in what genuinely
cannot be derived.

## 3. Create the repository

Choose where the new `infrastructure-live` repository should live and create it. The repository is created
empty; the following steps fill it with the Pipelines scaffold.

<Inputs id="repo" title="New repository">
```yaml
variables:
  - name: GitHubOrgName
    type: string
    description: The GitHub organization (or user) that will own the new repository.
    validations:
      - required
    x-section: Repository

  - name: GitHubRepoName
    type: string
    description: Name for the new infrastructure-live repository to create.
    default: infrastructure-live
    validations:
      - required
    x-section: Repository

  - name: Visibility
    type: enum
    description: Visibility of the new repository. "internal" requires a GitHub organization on a plan that supports internal repositories.
    options:
      - private
      - internal
    default: private
    validations:
      - required
    x-section: Repository
```
</Inputs>

Pipelines deploys from a single branch. Name it now — it becomes the new repository's initial branch, and
the setup pull request is opened against it.

<Inputs id="deploy" title="Deploy branch">
```yaml
variables:
  - name: DeployBranch
    type: string
    description: The branch Pipelines deploys from. Merges here trigger apply; this branch is granted the apply role.
    default: main
    validations:
      - required
```
</Inputs>

## 6. Configure the bootstrap

Fill in the values that cannot be derived automatically. Everything else is supplied for you from the
steps above.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: SubscriptionName
    type: string
    description: A short name for this Azure subscription (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Subscription

  - name: AzureLocation
    type: string
    description: The Azure region for the subscription's state-backend resources and OIDC infrastructure (e.g. "eastus").
    default: eastus
    validations:
      - required
    x-section: Subscription

  - name: StateResourceGroupName
    type: string
    description: Name of the Azure resource group that will hold the OpenTofu state storage account.
    validations:
      - required
    x-section: State

  - name: StateStorageAccountName
    type: string
    description: Name of the Azure storage account for OpenTofu state. Must be globally unique, 3-24 characters, lowercase letters and numbers only.
    validations:
      - required
    x-section: State

  - name: StateStorageContainerName
    type: string
    description: Name of the Azure Blob container within the storage account that holds the state files.
    default: tfstate
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the Entra ID resources. Creates <prefix>-plan and <prefix>-apply applications.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: Issuer
    type: string
    description: Optional override for the OIDC issuer URL. Leave blank to use GitHub's default (https://token.actions.githubusercontent.com).
    default: ""
    x-section: OIDC

  - name: IncludeDriftDetection
    type: bool
    description: Whether to generate the scheduled drift-detection workflow (.github/workflows/pipelines-drift-detection.yml).
    default: true
    x-section: Workflow

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced
```
</Inputs>

## 7. Generate the repository scaffold

Render the `azure/github/infrastructure-live` template into the empty repository. This writes the full
repository layout: `root.hcl` (with the `azurerm` remote-state block commented out until after bootstrap),
`.mise.toml`, `.gitignore`, `.gruntwork/repository.hcl`, the `.github/workflows/` Pipelines workflows
(`pipelines.yml`, `pipelines-unlock.yml`, and — when drift detection is enabled —
`pipelines-drift-detection.yml`), `.gruntwork/environment-<SubscriptionName>.hcl` (with placeholder
client IDs to be filled in after apply), `<SubscriptionName>/sub.hcl`, and the first subscription's
bootstrap stack at `<SubscriptionName>/bootstrap/terragrunt.stack.hcl`.

Before generating, resolve the latest catalog release so the bootstrap pins the newest version
automatically (unless you pinned a specific `TerragruntScaleCatalogRef` above).

## 9. Record client IDs and migrate state

Apply left the plan/apply application client IDs to be recorded, the `azurerm` backend commented out, and
the OpenTofu state on local disk. These three steps finalize the configuration: record the real client
IDs into the environment file, activate the remote backend in `root.hcl`, and push the local state into
the Azure storage account. All of these edits are committed as part of the pull request.

## 10. Open a pull request

Commit the generated scaffold and open a PR against your new repository. Because the repository started
empty, this pull request seeds it with the Pipelines configuration; opening it does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.SubscriptionName }}/`. To add another subscription later, re-run
this runbook against an existing repository, or use the add-subscription runbook, and choose a new
`SubscriptionName`.
