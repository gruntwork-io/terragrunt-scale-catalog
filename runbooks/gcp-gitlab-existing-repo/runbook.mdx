# Bootstrap Gruntwork Pipelines — GCP + GitLab (existing repository)

This runbook installs [Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview)
(Terragrunt Scale) into an **existing** `infrastructure-live` repository hosted on **GitLab**, targeting
one **GCP** project.

It provisions, per project, the Workload Identity Federation trust that lets your GitLab CI pipelines
authenticate to GCP with no long-lived credentials:

- a Workload Identity Pool and an OIDC provider for GitLab CI,
- a `plan` service account (read-only, used on merge requests), and
- an `apply` service account (used on merges to your deploy branch),

each with the IAM bindings that scope authentication to your GitLab group/project.

Wherever a value can be discovered automatically, this runbook does it for you — your GCP **project
number** is looked up from the project ID you provide. You only fill in what genuinely cannot be
derived (including your GitLab group and project names, which cannot be reliably discovered).

## 5. Configure the bootstrap

Fill in the values that cannot be derived automatically. The GCP project number is looked up for you in
the next step from the project ID you enter here.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: ProjectName
    type: string
    description: A short name for this GCP project (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Project

  - name: GCPProjectID
    type: string
    description: The GCP project ID (string identifier, e.g. "acme-dev-123456") you are bootstrapping Pipelines in.
    validations:
      - required
    x-section: Project

  - name: GCPRegion
    type: string
    description: The GCP region used to configure the Google provider and the GCS state backend.
    default: us-central1
    validations:
      - required
    x-section: Project

  - name: StateBucketName
    type: string
    description: Name of the GCS bucket for OpenTofu state. Must be globally unique and obey GCS bucket naming rules.
    validations:
      - required
    x-section: State

  - name: GitLabGroupName
    type: string
    description: The GitLab group (namespace) that owns the repository. Only CI pipelines in this group/project may authenticate.
    validations:
      - required
    x-section: GitLab

  - name: GitLabProjectName
    type: string
    description: The GitLab project (repository) name. Only CI pipelines in this group/project may authenticate.
    validations:
      - required
    x-section: GitLab

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the OIDC resources. Creates the <prefix>-pool / <prefix>-provider Workload Identity resources and the <prefix>-plan / <prefix>-apply service accounts.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: GitLabServerDomain
    type: string
    description: Domain of your GitLab server for self-hosted instances (e.g. "gitlab.example.com"). Leave empty to use gitlab.com.
    default: ""
    x-section: GitLab

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced
```

## 8. Add the GitLab CI configuration

An existing repository needs the Pipelines CI configuration added explicitly (the project template does
not include it). This writes `.gitlab-ci.yml` into the repo, wiring in the Gruntwork Pipelines CI/CD
component.

<TemplateInline
  id="gitlab-ci-file"
  inputsId={["deploy", "config"]}
  generateFile={true}
  target="worktree"
  outputPath=".gitlab-ci.yml"
>
```yaml
# Gruntwork Pipelines workflow. Runs plan on merge requests and apply on merge to the deploy branch.
# To upgrade Pipelines, bump the @ref on the component include below.
# Docs: https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview

workflow:
  name: GruntworkPipelines
  rules:
    - if: $CI_PIPELINE_SOURCE == 'merge_request_event'
    - if: $CI_COMMIT_BRANCH == "{{ .inputs.DeployBranch }}"

include:
  - component: $CI_SERVER_FQDN/gruntwork-io/pipelines-workflows/pipelines@v2

variables:
  # Full git history is required for Pipelines to accurately detect which units changed.
  GIT_DEPTH: 0
```
</TemplateInline>

## 10. Open a merge request

Commit the generated configuration, push a branch, and open a merge request against your repository.
Opening the MR does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup merge request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on merge requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.ProjectName }}/`. To add another project later, re-run this runbook
and choose a new `ProjectName`.
