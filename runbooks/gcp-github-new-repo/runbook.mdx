# Bootstrap Gruntwork Pipelines — GCP + GitHub (new repository)

This runbook creates a **new** `infrastructure-live` repository on **GitHub** and installs
[Gruntwork Pipelines](https://docs.gruntwork.io/2.0/docs/pipelines/concepts/overview) (Terragrunt Scale)
into it, targeting one **GCP** project.

It scaffolds the complete repository (root `root.hcl`, `.mise.toml`, `.gitignore`, the GitHub Actions
workflows, and the first project's bootstrap stack) and provisions, per project, the Workload Identity
Federation trust that lets your GitHub Actions workflows authenticate to GCP with no long-lived
credentials:

- a Workload Identity Pool and OIDC provider for GitHub Actions,
- a `plan` service account (read-only, used on pull requests), and
- an `apply` service account (used on merges to your deploy branch).

Wherever a value can be discovered automatically, this runbook does it for you — your GCP project number
comes from the project ID you provide, and the numeric GitHub org/repo IDs (used for GitHub's immutable
OIDC subject claims) come from the clone step. You only fill in what
genuinely cannot be derived.

## 4. Create your infrastructure-live repository

Name the new repository to create. It is created with an initial commit so it has a default branch to open
the setup pull request against.

<Inputs id="repo" title="New repository">
```yaml
variables:
  - name: GitHubOrgName
    type: string
    description: The GitHub organization (or user) that will own the new repository.
    validations:
      - required
    x-section: Repository

  - name: GitHubRepoName
    type: string
    description: Name for the new infrastructure-live repository to create.
    default: infrastructure-live
    validations:
      - required
    x-section: Repository

  - name: Visibility
    type: enum
    options:
      - private
      - internal
      - public
    description: Visibility of the new GitHub repository.
    default: private
    validations:
      - required
    x-section: Repository
```
</Inputs>

Pipelines deploys from a single branch. Name it now — it becomes the new repository's initial branch, and
the setup pull request is opened against it.

<Inputs id="deploy" title="Deploy branch">
```yaml
variables:
  - name: DeployBranch
    type: string
    description: The branch Pipelines deploys from. Merges here trigger apply; this branch is granted the apply service account binding.
    default: main
    validations:
      - required
```
</Inputs>

## 6. Configure the bootstrap

Fill in the values that cannot be derived automatically. Everything else is supplied for you from the
steps above.

<Inputs id="config" title="Bootstrap settings">
```yaml
variables:
  - name: ProjectName
    type: string
    description: A short name for this GCP project's environment (e.g. "dev", "prod"). Becomes the top-level directory and the Pipelines environment name.
    validations:
      - required
    x-section: Project

  - name: GCPProjectID
    type: string
    description: The GCP project ID to bootstrap Pipelines in (the string identifier, e.g. "my-project-123"). Resources are created here.
    validations:
      - required
    x-section: Project

  - name: GCPRegion
    type: string
    description: The GCP region used to configure the Google provider and as the location of the GCS state bucket.
    default: us-central1
    validations:
      - required
    x-section: Project

  - name: StateBucketName
    type: string
    description: Name of the GCS bucket for OpenTofu state. Must be globally unique and obey GCS bucket naming rules.
    validations:
      - required
    x-section: State

  - name: OIDCResourcePrefix
    type: string
    description: Prefix for the Workload Identity and service-account resources. Creates <prefix>-plan and <prefix>-apply service accounts and a <prefix>-pool Workload Identity Pool.
    default: pipelines
    validations:
      - required
    x-section: OIDC

  - name: IncludeDriftDetection
    type: bool
    description: Whether to render the scheduled drift-detection GitHub Actions workflow.
    default: true
    x-section: Advanced

  - name: TerragruntScaleCatalogRef
    type: string
    description: 'Optional: pin a specific Terragrunt Scale catalog ref (e.g. v1.13.1). Leave blank to use the latest release, resolved automatically before the generate step.'
    default: ""
    x-section: Advanced

  - name: TerragruntVersion
    type: string
    description: Terragrunt version to pin in the repository's .mise.toml. Optional — leave as the default unless you need a specific version.
    default: "1.0.0"
    x-section: Advanced

  - name: OpenTofuVersion
    type: string
    description: OpenTofu version to pin in the repository's .mise.toml. Optional.
    default: "1.11.5"
    x-section: Advanced
```
</Inputs>

## 10. Open a pull request

Commit the generated configuration and open a PR against your new repository. Opening the PR does not start a Pipelines run — the commit is tagged `[skip ci]`, and you have already applied the bootstrap locally. After it merges to your deploy branch, Pipelines takes over.

**You're done.** The setup pull request was committed with `[skip ci]`, so opening it does **not** kick off a Pipelines run — you applied this bootstrap locally on purpose, so Pipelines never runs against half-configured infrastructure. Once you **merge** it to `{{ .inputs.DeployBranch }}`, Gruntwork Pipelines is activated: from then on it runs `plan` on pull requests and `apply` on merges to `{{ .inputs.DeployBranch }}` for changes under `{{ .inputs.ProjectName }}/`. To add another project later, render the
`gcp/github/project` template into this repo (or re-run this runbook against the existing repository) and
choose a new `ProjectName`.
